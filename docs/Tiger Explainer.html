Tiger, explained

Tiger defines a restricted dialect of Go and checks that your code stays inside it. You run one command and get a verdict. The code conforms, or you get a list of exact edits to make. No warnings, no judgment calls, nothing to argue about in review.

tiger check binary verdict change detection

Why this tool exists

AI agents write more and more of our code. An agent is fast, tireless, and happy to hand you a function that loops forever on hostile input. Somebody has to hold the line, and doing it by human review means re-arguing the same points on every pull request.

Tiger holds the line mechanically. It restricts Go the way TigerStyle and NASA's Power of Ten rules restrict C for mission-critical software. Every loop provably ends. Every error is handled or its discard is justified. Every goroutine has a shutdown path. An AI-written change either conforms, or tiger check fails the build with findings the agent must fix. The cheapest path to a green build is the compliant rewrite, so that is the path the agent takes.

The second job is change detection. You can freeze a fact about your code (this function does no network IO, this loop ends because this value shrinks) into a comment called a pin. From then on, a change that silently breaks the promise fails the build. An agent cannot drift your assertions and claims without you seeing it in review.

What it caught before you met it

Tiger was trialed on two real codebases before its rules settled. A distributed queue (about 42,000 lines of hand-written Go) and a git server (about 17,000). The rules found ten real bugs between them. The worst one was remotely triggerable, a denial of service in the git server. A client could push two tags whose headers point at each other, then ask the server to resolve one. The resolving loop had no depth cap and no cycle check, so one request would spin a goroutine at 100% CPU forever. The loop-bound rule flagged it as an unbounded loop, which is exactly what it was.

RuleReal bugs found
TS-S02 every loop has an upper bound5, including the DoS and a pause/shutdown deadlock
TS-S08 a switch over a fixed set handles every case3, all silently dropping data on unexpected values
TS-C05 blocking waits are cancellable1, client waits that could never be cancelled
TS-C02 goroutines start through a supervisor1, shutdown returning before its goroutines exited
TS-E02 discarding a result needs a justification1, a discarded validation error set to corrupt IDs later

Every one of these passed the race detector, the test suite, and human review before tiger saw the code. And in both trials, a false positive on a blocking rule was treated as a bug in tiger. It got fixed in the analyzer with a regression test, never suppressed in the target code. Zero suppressions across both trials.

What a linter is, and why tiger is not one

If you have never used a static-analysis tool, here is the whole idea. A program can read your source code without running it. Not as text (that would miss too much) but as the same structure the compiler builds, a tree where a loop is a loop node and a function call is a call node, whatever the whitespace looks like. Compiler folks call this tree an AST, short for abstract syntax tree. A tool that walks this tree can answer questions like "does this loop's condition ever change?" precisely, the way a text search never could.

A linter is such a tool that looks for likely problems and prints warnings. Warnings pile up, people learn to ignore them, and every team ends up arguing about which ones matter. golangci-lint, the standard Go linter runner, is good at this job, and tiger leans on it for the rules it already enforces well.

Tiger itself does something narrower and harder. It checks membership in a dialect. Every tiger rule is exact within its stated scope, and every finding is a verdict, not an opinion. If tiger prints a finding, the build is red and the finding names the edit that fixes it. If tiger is wrong, that is a bug in tiger, you file it, and the fix lands with a regression test. Warnings about possible issues remain golangci-lint's job.

What you touch

One command in CI and locally. Four subcommands total (check, budget, golangci, pin). Two committed YAML files. A handful of //tiger: comments in your source.

Inside (not your concern)

Thirty-plus analyzers walking your code's structure, computing what each function does, what it writes, and why each loop ends, then comparing all of it against the rules and your declarations.

1. Run the check

Say you write this. It compiles, it is idiomatic Go, and reviewers wave it through every day.

// Drain consumes entries until none remain.
func Drain(entries <-chan uint32) uint32 {
    var total uint32
    for entry := range entries {
        total += entry
    }
    return total
}
$ tiger check ./...
drain.go:6:2: TS-S02: this loop ranges over a channel, so it ends only when some other goroutine closes the channel — add a counter cap that fails when the cap is hit, or make it an event loop that selects on ctx.Done()
tiger: 1 blocking

That is a real transcript. Notice what the finding line does. It names the rule (TS-S02), says what the code actually does, and names two concrete edits that fix it. You never need tiger vocabulary to act on a finding. When you want the reasoning behind a rule, you look its code up in the rule reference.

A clean run prints nothing and exits 0. Output is a verdict, so silence is the good news, and two runs on the same code produce byte-identical output.

2. Pin what matters

While checking, tiger also computes facts about your functions. What effects they have (allocate, do IO, block, panic, read time or randomness, mutate, spawn), and what they write through their parameters. Facts are not findings. They print only when you ask.

$ tiger check --show-facts ./...
header.go:34:1: TS-F01: EncodeHeader's effects are alloc — nothing to fix; to make tiger fail the build if they change, add //tiger:effects alloc

The fact prints as the exact comment you would paste. Freezing it is called pinning, and tiger pin writes the comment for you.

$ tiger pin EncodeHeader
header.go:35: //tiger:effects alloc
header.go:36: //tiger:frame none

A pin changes nothing at run time. It changes what CI enforces. Suppose someone (or some agent) later makes the pinned function block on a channel. The next check fails.

drain.go:5:1: TS-F01: this function blocks (channel receive at drain.go:8:2) but its //tiger:effects comment doesn't list block — add block to the comment, or remove that code

There are two honest exits. Change the code back, or change the pin. A pin edit is visible in the diff, so the reviewer rules on the new promise. A pin can never go stale, because a wrong pin is a failed check, not a lie in a comment.

ConditionWhat tiger doesMerge
No pin; the function's behavior changesNothing (the fact just has a new value)Continues

The concepts, in order

Rules and the two severities

Every rule has a code like TS-S02 and exactly one of two severities. Blocking findings fail the run. Advisory findings are counted, not printed. There is no warning tier, on purpose. A rule either blocks or it is not a rule, so nothing tiger prints can be weighed and set aside.

Advisory exists for exactly two standing facts of real code, an escape directive and a skipped test. Both are legitimate, both are worth bounding, so tiger counts them against a per-package budget instead of pretending they are errors.

The budget and the ratchet

tiger.budget.yaml is a committed file with one number per package per advisory rule, the count that package is allowed to carry. Under budget, nothing prints. Over budget, the run fails and the counted findings print. tiger budget --write records current counts, and it can only lower numbers. Raising one is a hand edit that a reviewer sees in the diff. Debt shrinks automatically and grows only over somebody's signature. Tiger calls this the ratchet.

Directives

A directive is a //tiger: comment on the line above the thing it describes. The vocabulary is closed and a typo is a blocking finding, so a directive cannot silently do nothing. There are three kinds.

1
Pins
Freeze a computed fact into a contract. //tiger:effects, //tiger:frame, //tiger:variant. Optional, and written for you by tiger pin.
freeze
2
Intent declarations
State something no analyzer can compute, and the code is held to the statement. //tiger:restrict, //tiger:openenum.
declare
3
Escape hatches
Loosen one rule at one site, with a mandatory reason. There is exactly one, //tiger:batched, and every use is counted against the budget on every run.
counted

Why only one escape hatch? An escape is admitted only when reality, not convenience, demands it. Some external systems accept one item at a time, and no rewrite of your code changes that, so //tiger:batched <reason> exists. A general "ignore this rule here" directive does not exist and will not. An agent offered a comment-shaped path to green will take it, so the only paths are the compliant rewrite or a counted, human-reviewed escape.

What adoption actually looks like

Honest numbers, from the trials. The queue's first run produced 1,023 blocking findings. The git server's produced 712. That is what pointing a strict dialect at good, existing, hand-written Go looks like, and it is why adoption is a decision about a codebase's future, not an afternoon's chore. On a fresh codebase where the code is AI-written against the rules from day one, the count starts at zero and stays there.

The escape hatch earned its keep in the trials. The queue had 24 loops that drain a database cursor, a shape only the backing store bounds. Each got //tiger:batched with its reason. The loop-bound rule went from 37 findings to 11, every waiver became a counted, reviewable line in the budget, and the one real deadlock among those findings kept firing. That is the design working, silence for the declared facts of the world, noise for the bug.

Plugin caveats Tiger also runs inside golangci-lint as a plugin, but two things need the real CLI. Budgets (the plugin has no end-of-run step to count against them, so it reports every counted finding as an issue) and the three whole-program rules that need evidence from every package at once. Run tiger check in CI; use the plugin for editor integration.

What tiger will not do

No warnings. No per-site suppression comments. No "informational" output on a normal run. If a rule's findings turned out to be noise on real code, the rule was removed from tiger entirely rather than demoted to a warning; three naming rules died exactly that way during the trials. A smaller set of rules people actually fix beats a large set people learn to scroll past.

Tiger also does not replace golangci-lint, it configures it. Style opinions, probable-bug heuristics, and the rest of the linting world stay where they are.
