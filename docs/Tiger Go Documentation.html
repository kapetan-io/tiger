Tiger Go

A Go dialect where the specification lives in the source and a machine checks that the code matches it. You write Go plus a small layer of declarations. The tiger analyzer checks the correspondence between them on every pull request. A change that touches no declaration and passes CI merges without a human reading it.

The premise

One economic claim sits above everything:

The claim The cost of a defect grows super-linearly with the distance between the moment it is introduced and the moment it is detected. Distance means time, stack frames, call sites, service hops, and releases.

Every rule in Tiger Go is one of three strategies against that curve: shrink the population of possible defects, shorten the distance to detection, or bound the damage while the distance is being travelled. The goal order (safety, then performance, then developer experience) is a statement about detection distance: a safety defect is detected by a customer, a performance defect by a dashboard, a developer-experience defect immediately by the person typing.

Tiger Go is not a style guide. It is a restriction of Go, chosen so that questions a reviewer normally answers by reading become questions a tool answers by checking. The formatting rules are a side effect, not the point.

Enforcement is split between two engines from the start. Rules an existing linter already checks are auto rules: delegated to roughly fifty off-the-shelf golangci-lint linters (errcheck, funlen, depguard, …) pinned to a required baseline configuration at config/golangci.yml. Tiger never reimplements one. Rules no existing linter can check are custom rules, enforced by the analyzers the tiger binary ships. Both engines are the dialect: run only one and half of Tiger Go is unenforced. So when a linter name appears anywhere in this document, that linter is carrying a Tiger Go rule, and tiger golangci exists to audit that the project's config still carries them.

How review divides

The split is not by topic and not by directory. Every concern has two parts, and the parts get different treatment.

Humans and AI review the declarations

Is SequenceMonotonic the invariant this protocol actually needs? Should this function be permitted to touch the disk at all? Is 512-byte sectors true of the hardware? Can the Storage interface express a torn write? These are claims about the world, and no analyzer contains a representation of the world.

Machines check the correspondence

Does the code satisfy the invariant it names, stay inside its declared frame, terminate, cover every state, match its effect set, route its nondeterminism through an injectable surface, respect the declared layering? These are relations between two artifacts the machine can see, and they are checked on every pull request.

The declarations are a layer, not a region. They cut across every file. There is no part of the tree that is "the reviewed part." The policy that falls out:

The policy A change touching no declaration and passing CI merges without a human reading it. A change touching a declaration goes to someone who knows the domain, and nothing else about it is discussed, because everything else has already been checked.

Track one number and make it the headline: the fraction of merged lines that no human read. It starts near zero. If adoption chains 1 and 3 complete, it should pass half.

1. Write code; the analyzer reports

func SaveHeader(h Header) error {
    return os.WriteFile(h.Path, h.Bytes(), 0o644)
}
── tiger: effect report ───────────────────────
SaveHeader changed   (was: none)
//tiger:effects io(disk)

The report does not stop the merge. It prints the computed fact in pin syntax, the exact line you would paste above the function. Report and pin share one format; there is nothing to translate.

2. Pin what matters

//tiger:effects io(disk)
func SaveHeader(h Header) error {
    return os.WriteFile(h.Path, h.Bytes(), 0o644)
}

A pin freezes the computed fact into a contract. From now on, any change that makes the code disagree with the pin fails the CI check on the pull request, before merge, with both lines shown in the same format:

── tiger: effect check ────────────────────────
store/header.go:14:1: TS-F01: SaveHeader — the code does not agree with the pin
  pin:      //tiger:effects io(disk)
  computed: //tiger:effects io(disk), io(net)
Fix: remove the io(net) call, or replace the pin with the computed line.

There are two honest exits. Change the code, or change the pin. A pin change is visible in the diff, so the reviewer rules on the new promise. A pin can never go stale: a wrong pin is a failed check, not a lie in a comment.

The four rules of the analyzer

ConditionAnalyzer actionMerge
No pin; effects changeReport in the pull requestContinues

Where pins may go Function-scoped pins attach to exported functions and methods only. Unexported helpers are the region mechanical refactoring must be free to reshape, and nothing is lost: a pin bounds its entire callee subtree, so exported pins constrain unexported internals transitively, with the failure naming the introducing call. Sparse pins give dense enforcement. (Loop variants are the placement exception; a variant pin attaches to its loop.)
The trigger rule Most pins are optional. When a package declares closed dispatch (TS-K03 under TS-P01), pins become required on its exported functions. Pins attach exactly where the computed facts are exact, a defined event, not a mood.

Core concepts

Enforceability is a property of a rule in a language

The insight the whole dialect is built on: the analyses that are undecidable in general Go are almost all decidable in Go restricted by the other rules. The analysis does not get smarter. The language gets smaller. The restrictions compound in a specific order:

no globals + no unsafe + no reflection
  → the heap graph is reachable only through parameters and receivers
    → points-to analysis is exact for the fragment
      → frame conditions are checkable
        → "what can this function change" is machine-answerable
          → mechanical refactoring is provably behavior-preserving
            → refactoring diffs need no review

Each link is worthless alone. In the chain, each is load-bearing for a guarantee five steps away. The practical consequence: you do not get sixty percent of the value from sixty percent of the rules. You get very little until a chain completes, and then a lot at once. Adopt by chain, not by ease.

Judgment is conserved

You can relocate judgment; you cannot delete it. Every rule promoted from review to lint moves a judgment out of the code and into a declaration, and someone still has to be right about the declaration. It is a good trade for three measurable reasons: the declaration layer is small (typically two to five percent of lines), stable (changing an order of magnitude less often than the code it governs), and dense (attention spent there is spent where being wrong is most expensive).

The effect lattice

Effects are the vocabulary the analyzer computes and pins freeze. The lattice is closed and small; absence of all effects is purity.

EffectMeaning
allocHeap allocation: the hot-path gate (TS-F03)

blockCan block (channel ops, locks); excluded from critical sections (TS-F05)

Effects are transitive by construction: if your helper writes to disk, you write to disk. This is what turns a name-based ban (TS-C08: no time.Sleep) into a guarantee that cannot be laundered through three frames of indirection. An empty effect set is purity, and in a pin it is spelled //tiger:effects none, because absence of a pin never means purity; it means unpinned.

The io qualifier vocabulary

The vocabulary has two tiers, and both are closed sets.

TierQualifiersDetected by
Built-inio(disk), io(net), io(exec), io(env)Standard-library facts; zero configuration
DeclaredProject-defined, e.g. io(database), io(cache)Anchored to a declared surface (TS-I01): the analyzer infers the qualifier for any function whose call graph reaches the surface (exact, not heuristic)

A pin may only use qualifiers that exist, built-in or declared, so a misspelled qualifier is an error rather than a silently meaningless string. The declared tier is visibility: pin the Store methods with io(database), and any other function that acquires the effect, through any indirection, surfaces in the PR as an architecture violation. The hard wall is the import restriction (TS-P01): only internal/store may import the database driver. Use both together.

The scoping model

Function scope: computed

Effects, frames, contracts, and variants are properties of a single function, derived from its body and its callees. No boundary, no region to defend, only a gradient.

Package scope: declared

Import allowlists, dependency bans, dispatch closure, and layering can only be package-scoped, because Go's import granularity is the package.

Restrictions are declared with //tiger:restrict ... in the package doc comment, and every undeclared axis takes a stated default, absence is never an error. Imports default to stdlib-only, dispatch to open, layering to the TS-X03 layer file. Weakening is never silent, either: TS-P03's surface-diff obligation also covers a drop in the computed TS-P02 precision bound (annotation-only, firing only when the bound's value changes).

Package restrictions are enablers, not tiers. They determine the precision of the function-level checks, not whether those checks run. A package that permits dynamic dispatch still gets effect analysis, as a conservative over-approximation at lower confidence. The result is a precision gradient rather than a wall, which matters because a wall gets argued about, eroded, and exempted, and a computed property does not.

The assert package

Go has no assert. This is the single largest gap between TigerStyle and idiomatic Go, and nothing else works until you close it. Draw the line clearly and keep it drawn:

The line An error is an expected operating condition the caller must handle. An assertion failure means the code is wrong, and the only correct response to wrong code is to crash.

A disk returning ErrNotExist is an error. A function receiving a negative length is a bug, and returning an error for it launders the bug into a caller who can do nothing about it either. Assert it and die. Assertions stay enabled in production. The ones you compile out only ever protected your test suite. They downgrade correctness bugs into liveness bugs, which is the trade you want.

FunctionUse
assert.Ok(cond, msg)The general form. msg must be a constant string; no allocation on the fast path.
assert.Implies(a, b, msg)The Go replacement for single-line if (a) assert(b), which gofmt forbids.
assert.Equal(got, want, msg)Equality with both values in the failure message.
assert.Between(v, low, high, msg)Inclusive range check. Say what you mean about the ends of a range.
assert.Index(i, count, msg)Valid index into a container of length count.
assert.NoError(err, msg)Only where an error is structurally impossible (e.g. writing to bytes.Buffer).
assert.Unreachable(msg)The default arm of a switch over a closed set.
assert.Fail(format, args...)Formatted failure. Call inside an if, never as the whole assertion.
assert.Invariant(id, cond)Assert a named invariant; see the invariant vocabulary below. At run time this is Ok; the ID exists for the analyzer (TS-A07–A09). Generic over ~string, so assert imports nothing.
assert.Violates(id, func())Runs the function and fails unless it violates the named invariant, the negative-space proof TS-A09 requires. Foreign panics are re-raised, not swallowed.

Two Go-specific traps shape the API. Variadic arguments are boxed at the call site before the callee tests anything, so there is no formatted variant of Ok. Formatting lives behind an if that only runs on failure. And inlining has a budget, so the failure path is a separate //go:noinline function; the fast path compiles down to a predictable branch.

The invariant vocabulary

Stop passing strings to assertions. Declare each invariant once, in one package, and reference it by ID. Properties an analyzer could never see in two boolean expressions become reference counting and set equality.

// Package inv declares every invariant the storage engine enforces.
package inv

type ID string

const (
    HeaderChecksum    ID = "header-checksum"    // Header checksum matches the payload.
    HeaderSize        ID = "header-size"        // Header occupies exactly HeaderSizeBytes.
    SequenceMonotonic ID = "sequence-monotonic" // Sequence numbers never decrease within a term.
)
func encodeHeader(target []byte, h Header) {
    assert.Invariant(inv.HeaderSize, len(target) == HeaderSizeBytes)
    assert.Invariant(inv.HeaderChecksum, h.Checksum == checksum(h.Payload))
}

Three rules make the vocabulary load-bearing:

1
TS-A07: every invariant asserted in at least two functions
Pair assertion, restated as something countable. Asserted once = misfiled or under-defended.
invariantrefs
2
TS-A08: symmetric boundaries assert the same set
encode/decode, marshal/unmarshal, write/read pairs must defend identical invariant sets.
invariantsymmetry
3
TS-A09: every invariant has a test that violates it
If no test can make it fail, the invariant is unreachable or the assertion is wrong.
invariantnegative

What falls out: grep an invariant and get every site defending it; the invariant list is a design document that cannot go stale (a deleted assertion fails TS-A07); and a fake invariant costs more work than thinking of a real one.

Directive reference

All source declarations share one namespace: //tiger:<verb>, following Go's own directive convention (//go:build, //go:generate). Three kinds, with different lifecycles:

Pins

A pin is computed by default and blocking once written. The analyzer infers the fact and reports changes; writing the directive freezes the fact into a blocking contract. Function-scoped pins attach to exported functions and methods only, and each pin bounds its entire callee subtree (TS-F02). A pin changes nothing at run time, only what CI enforces.

//tiger:frame r.log, r.checkpointWhat the function may write; writes outside the frame failTS-F07
//tiger:variant len(pending)Loop termination measure: strictly decreases on every back edge, bounded belowTS-V01

Escape hatches

An escape hatch is earned, reasoned, and never silent.

The admission test An escape hatch exists only where the restricted dialect eliminates something reality requires, where no in-dialect rewrite can comply. This is the admission test, and inconvenience never qualifies: the primary consumer is an AI agent, and an agent offered a cheaper path than conforming will take it. A directive's reason is shape-checked (verb known, reason present, TS-L09), never truth-checked, so every escape in the tree also surfaces as a standing advisory finding on every run, and the per-package directive count stays a first-class ratchet metric (TS-D06).
DirectiveStatusRule
//tiger:batched <reason>The one admitted escape: an external system that only accepts per-item IO is a fact of the world no rewrite removesTS-M10
//tiger:bounded <reason>Withdrawn: fails the admission test. Every terminating loop has an in-dialect shape, an explicit cap with an assert or error on exhaustion, or the TS-S03 event-loop form. The verb does not parse; it is an unknown-verb errorTS-S02
//tiger:<rule-id> <reason>Gated: ships, if ever, together with the first heuristic rules and the TS-D06 ratchet (mechanism and control in one release). Until then, an unknown-verb errorTS-L09

There is no //nolint-style dismissal anywhere in the dialect. When a rule fires, the paths out are: fix the code (the finding names the compliant shape), declare the one earned escape if the world forces the shape, or, if you believe the finding is wrong, file a bug, because a false positive on a blocking rule is a defect in the analyzer, not a condition your code absorbs.

Example: the uncapped loop, and the escape that earns its place

// First draft — the retry loop spins forever on a permanently-failing hook.
func (n *Notifier) Flush(ctx context.Context) error {
	for !n.queue.Empty() {                      // TS-S02 fires: no derivable bound
		for _, hook := range n.queue.Next() {
			if err := post(ctx, hook); err != nil {
				n.queue.Requeue(hook)
			}
		}
	}
	return nil
}

There is no directive to reach for. The fix is in-dialect. Make the retry budget a real, named number, and decide what exhaustion means (undelivered hooks are an expected condition, so an error, not an assert):

// FlushPassesMax = first attempt + 2 retries.
const FlushPassesMax = 3

func (n *Notifier) Flush(ctx context.Context) error {
	for pass := 0; pass < FlushPassesMax; pass++ {   // bound is counter-derived — proved
		if n.queue.Empty() {
			break
		}
		//tiger:batched provider offers no bulk endpoint; contract caps us at 10 rps
		for _, hook := range n.queue.Next() {
			if err := post(ctx, hook); err != nil {
				n.queue.Requeue(hook)
			}
		}
	}
	if !n.queue.Empty() {
		return fmt.Errorf("%d hooks undelivered after %d passes", n.queue.Len(), FlushPassesMax)
	}
	return nil
}

notifier.go:18:3: TS-L09 [advisory]: escape //tiger:batched — "provider offers
no bulk endpoint; contract caps us at 10 rps" (unverified claim; standing review)

The rule catalogue

145 rules across 15 areas. Every rule has an ID (TS-<area><nn>), a rationale tracing to a named benefit (B0–B8), and an enforcement mechanism. Enforcement levels: auto (off-the-shelf linter), custom (an analyzer specified in the implementation plan), partial (heuristic, expect false positives), runtime (test or CI gate), review (human judgment; the reason is always that the declaration is a claim about the world). Severity is blocking unless stated; on a legacy codebase, start advisory and ratchet per package.

Full rule text, rationale chains, and the complete traceability matrix live in Tiger Specification.md. Distribution: B3 local reasoning (44 rules) and B2 short defect distance (40) carry the document; 9 rules are pure convention, and the spec says to know that number rather than pretend it is zero.

Thresholds are calibrated, not derived Twelve numbers (70 lines, 100 columns, cyclomatic 10, nesting 3, …) are calibration points. The existence of each bound is justified by a benefit; the particular number is a starting point. Changing a number needs data from your codebase and is normal. Removing a bound needs an argument against the benefit, and is not.

Surfaces and simulation

Co-equal with the rule catalogue, not a testing detail. The rules make properties checkable; surfaces make the checked properties describe the running system rather than a model of it.

Every nondeterministic effect (time, randomness, IO, scheduling, identity) must reach the system through a declared surface (TS-I01). A function calling time.Now() directly cannot be replayed, and a system with one such call cannot be simulated. Prefer description (code returns commands as values; something else interprets them) where the shape allows; require injection (code takes a Storage interface) everywhere else.

1
Design the interface around its faults (TS-I05)
If a real disk can produce a torn write and your Storage interface cannot represent one, the simulator is structurally blind to that bug class and runs green forever. Uglier interfaces are the point.
review
2
Two implementations, one conformance suite (TS-I03)
Every surface has a production and a simulated implementation, and both pass the same suite, or you have verified a world that does not exist.
surfaces
3
The simulated one is the adversary (TS-I04)
Inject every fault the spec allows, not the ones you have happened to observe. A fake that behaves better than reality hides the bugs the simulator exists to find.
runtime
4
Adapters contain no logic (TS-I06); fidelity is config (TS-I07)
A branch in an adapter is a decision the simulator never sees. The same suite runs fully simulated, partially simulated, and fully real, differing only in injection config.
surfaces

The tiger CLI

One command-line program, ordinary static analysis built on Go's go/analysis framework, the same family as go vet. Deterministic: no LLM, no network; the same source tree produces byte-identical output, verified in CI by running the suite twice and diffing. All custom analyzers (57 planned; the 20 computed-only ones are wave 1) ship in one binary via subcommand dispatch, and as a golangci-lint module plugin so they run in the same pass as the ~50 off-the-shelf linters the config already enables.

WhereWhenResult
Your machinetiger check ./..., any timeReports and blocks before you push
CIAutomatic, every pull requestReports in the PR; a broken pin or violated rule fails the check; the reviewer sees both

Exit codes: 0 clean, 1 at least one blocking finding, 2 operational failure (any package failing to load or any analyzer failing to run exits 2). Partial results are never presented as a clean or complete run.

tiger golangci

Tiger enforces only the custom rules; the auto rules live in golangci-lint. That delegation can silently rot. A project's .golangci.yml missing half the required linters is half the dialect unenforced with nothing saying so. tiger golangci closes the gap: it audits the project's golangci-lint configuration against the registry's auto-rule baseline (every required linter enabled, every baseline setting at its expected value; extra linters and settings always pass, but a stricter-than-baseline value currently fails with a message saying it is stricter; direction-aware comparison is future work), reporting each gap as a finding that names the auto rule that stopped being enforced. tiger golangci --init generates the baseline config for a project that has none (module path filled in from go.mod) and refuses to touch an existing file. Exit codes mirror tiger check.

$ tiger golangci
.golangci.yml: TS-E01: errcheck is not enabled — every error must be handled;
enable errcheck with check-blank: true
.golangci.yml: TS-S04: funlen.lines is 120, baseline requires 70
exit status 1 — the dialect is only partially enforced until the config conforms

In wave 1 this costs little (19 of the 20 analyzers are blocking-only), but know which driver you're reading.

Alongside the analyzer, CI runs the runtime gates: -race always, goroutine-leak checks per package, seed-logged simulation runs, error-path coverage with its own floor, the nightly mutation score, the run-twice-and-diff determinism check, and the per-package budget ratchet (TS-D06). The ratchet covers complexity, directive count, skipped tests, assertion density, and hot-benchmark allocations, all committed to a file that can only decrease.

Adoption

The chains only pay when complete, so build in dependency order rather than by ease. Off-the-shelf linters reach roughly 80% mechanization in an afternoon; the promoted rules reach 96% for about 40 cheap analyzers; the last few percent costs an effect system, a points-to analysis, an abstract interpreter, and a refactoring prover.

Limits, honestly

What no amount of tooling fixes

Six items remain in a codebase where every rule is enforced, and they are all the same kind of thing: is this the right invariant; are the derivation's inputs true; is the contract right; is the fault model complete; should this effect be permitted; is this the right product.

The specification gap A machine can prove code satisfies a specification. Nothing can prove the specification is the right one, because rightness is a relation between the specification and the world, and the code contains no representation of the world. This is not a limitation to engineer around. It is the correct final resting place for human attention.

The engineering limits

  • Goodhart applies with force. Once conformance is the merge criterion, conformance gets optimized. The defence is the proxy test plus one genuine external oracle, the mutation score (TS-T08). A rising conformance score against a flat mutation score is a fire.
  • False positives are the real failure mode. An analyzer wrong 2% of the time on a blocking rule, across a thousand merges, is twenty forced directives, and directives are how a dialect degrades into a style guide with extra steps. Treat every forced directive as a bug report against the analyzer.
  • Cost is exponential in the tail. Whether the last few percent is worth an effect system and a refactoring prover depends entirely on how expensive your defects are, which is why this is a good idea for a database and a bad idea for most software.
  • You are hiring for a language nobody knows. Onboarding is longer and some good engineers will not want to work this way. The precision gradient is the mitigation, and it is a partial one.
