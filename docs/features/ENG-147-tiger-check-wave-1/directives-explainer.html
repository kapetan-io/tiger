Your build is red. Now what?

You write Go in a project checked by tiger check, and a finding just failed your build. This page explains your moves: fix the code into the shape the finding names, or — in exactly one earned case — declare a constraint of the outside world. There is deliberately no move that just makes a finding disappear.

What you see when a rule fires

Every finding tells you three things: which rule fired, what it saw, and what the compliant form looks like. You never need to open the specification to act on one.

Notice the finding names the compliant shapes directly. Which move is right depends on which of two situations you're actually in.

Almost every finding has an in-subset fix

The normal case  "Your code has the banned shape"

A goto, a naked panic, an uncapped loop, two same-typed parameters. Every wave-1 rule is exact — when it fires, the shape is really there — and every banned shape has a compliant rewrite inside the dialect, named in the finding. Your move: fix the code.

The rare case  "The outside world forces this shape"

Sometimes reality bans the rewrite: a provider with no bulk endpoint makes one-call-per-item the only possible code. For exactly these cases — where no rewrite inside the dialect can comply — a rule admits an escape hatch you declare with a reason.

The admission test An escape hatch exists only where the restricted dialect eliminates something reality requires. Inconvenience never qualifies. Wave 1 admits exactly one escape: //tiger:batched. And be clear about what the tool checks: an escape is shape-checked, never truth-checked — tiger verifies the verb is known and a reason is present, but the truth of your reason is a claim for human review. That's why every escape in the tree stays on the report as a standing advisory finding: unverified claims never sink out of view.

Why there is no //tiger:bounded

The rule (TS-S02): every loop states its upper bound. Most loops state it in their own syntax, and the tool proves it without your help:

// The bound is visible: len(entries). Silent — nothing to do.
for i := 0; i < len(entries); i++ { apply(entries[i]) }

// The bound is visible: a constant. Silent.
for attempt := 0; attempt < RetriesMax; attempt++ { ... }

Some correct loops hide their bound, because the termination argument lives in your head, not in the syntax:

// Converges — you know it, the tool can't. TS-S02 fires.
for !converged(estimate) {
    estimate = refine(estimate)
}

You might expect a //tiger:bounded "trust me, it converges" comment here. Tiger deliberately doesn't have one — because the tool could check that the comment exists, never that it's true. A trust-me comment is a suppression wearing a costume. And it fails the admission test, because the dialect never eliminated your ability to write this loop — it asked you to make the bound explicit, which you always can:

// The bound is now real, visible, and machine-proved — and if your
// convergence belief is ever wrong, you find out here, loudly, instead
// of hanging a core forever.
for i := 0; i < NewtonItersMax; i++ {
    if converged(estimate) { break }
    estimate = refine(estimate)
}
assert.Ok(converged(estimate), "no convergence within NewtonItersMax")

This is the dialect's philosophy in one rewrite: everything in reality has a limit — pick the number. A bound picked slightly wrong fails locally, early, at a boundary you wrote; a trusted comment that was wrong fails globally, late, and far from the cause. Genuinely-forever loops (servers, event loops) aren't capped either — they get their own compliant shape (TS-S03: select on ctx.Done()), also with no directive.

Where this is headed A later wave (the termination chain) upgrades this again: the analyzer will prove loops terminate by verifying a decreasing expression on every iteration — machine-checked where today you pick a cap. The direction of travel is always toward checked, never toward trusted.

//tiger:batched — the one escape that earns its place

The rule (TS-M10): no IO inside a loop body. A write, query, or request per iteration is the anti-batching shape — it's every N+1 query ever written, and it's the pattern that turns one network round-trip into ten thousand:

// TS-M10 fires: one INSERT per iteration. The fix is almost always
// to batch — and the finding says so.
for _, entry := range entries {
    db.Insert(ctx, entry)
}

// Compliant: one round-trip.
db.InsertBatch(ctx, entries)

Here is the difference from the loop-bound case: no rewrite can fix this one when the provider simply has no bulk endpoint. The constraint lives in the outside world, not in your code — which is exactly what the admission test requires of an escape:

//tiger:batched provider offers no bulk endpoint; rate limiter caps us at 10 rps by contract
for _, hook := range webhooks {
    notify(ctx, hook)
}

The tool checks the shape — known verb, reason present (a missing reason is itself a finding, TS-L09). It cannot check whether the provider really lacks a bulk endpoint; that's your claim. So the claim doesn't get to disappear: every escape directive in the tree shows up as an advisory finding on every run — it never fails the build, and it never leaves the report. If the provider ships a bulk endpoint next year, the standing marker is how the loop gets found and fixed.

Wave-1 timing The batched verb is understood by the wave-1 tool (it parses, it demands a reason, it surfaces as advisory), but the analyzer that enforces TS-M10 arrives in wave 1.5. Declaring it early is fine and forward-compatible.

"Can't I just make the finding go away?"

No — and this is a feature, not a missing feature. Here is your complete decision tree when a wave-1 rule fires:

A rule fired on your code
exit 1, finding printed
↓does a rewrite inside the dialect comply? (almost always)
Fix the code
the compliant shape is named in the finding — cap the loop, split the condition, drop the goto
↓unless the outside world forbids the rewrite…
Declare the world's constraint
//tiger:batched <the real reason> — shape-checked now, standing advisory forever, judged by humans
↓and if you believe the tool itself is wrong…
That's a bug in tiger — file it
a false positive on a blocking rule is a defect in the analyzer, fixed in the analyzer

What's deliberately absent: a general-purpose comment that dismisses any finding — the //nolint of other linters. Every wave-1 rule is exact: if it fires, your code really has the shape the rule bans. There is no "the tool is probably confused" case to escape from. So an escape comment would have exactly one remaining use: avoiding the fix.

Why this matters more with AI In a Tiger codebase most findings are fixed by an AI agent, and an agent given a one-line escape will learn to write the escape — with a perfectly plausible reason attached — instead of doing the work. It's the cheapest token path to a green build. The tool refuses to offer that path: an unknown directive like //tiger:TS-N07 trust me doesn't parse. It is a blocking error, not a loophole.

If a rule ever blocks you unfairly, the pressure lands where it can fix the root cause: on the analyzer. That is a design commitment of the project — a false positive on a blocking rule is a bug in tiger, and adding rules is gated on that staying true. Later waves will add heuristic rules that genuinely can be wrong; a per-site deviation mechanism ships with those rules and with its accounting (deviations counted, tracked, and only allowed to decrease) — never before.

A worked example, end to end

Here's the full loop — write, check, fix, check — on a small notifier an AI agent might produce on its first pass. It has both kinds of problem: a loop whose bound nobody stated, and per-item IO forced by the outside world.

// notifier.go — first draft
func (n *Notifier) Flush(ctx context.Context) error {
	for !n.queue.Empty() {                      // how long can this run?
		for _, hook := range n.queue.Next() {
			if err := post(ctx, hook); err != nil {
				n.queue.Requeue(hook)   // failures loop back — potentially forever
			}
		}
	}
	return nil
}
$ tiger check ./...
notifier.go:12:2: TS-S02: this loop's bound cannot be derived from a constant,
a len, or a counter — give it an explicit cap with an assert or error on
exhaustion, or use the ctx.Done() event-loop shape (TS-S03)
exit status 1 — blocking finding, build is red

The requeue makes this genuinely unbounded: one permanently-failing webhook spins the loop forever. There is no directive to reach for — the fix is to make the retry budget a real, named number, and decide what happens when it runs out. Undelivered hooks after the budget is spent are an expected operating condition, so they become an error the caller handles, not an assert:

// FlushPassesMax = first attempt + 2 retries.
const FlushPassesMax = 3

func (n *Notifier) Flush(ctx context.Context) error {
	for pass := 0; pass < FlushPassesMax; pass++ {   // bound is counter-derived — proved
		if n.queue.Empty() {
			break
		}
		//tiger:batched provider offers no bulk endpoint; contract caps us at 10 rps
		for _, hook := range n.queue.Next() {
			if err := post(ctx, hook); err != nil {
				n.queue.Requeue(hook)
			}
		}
	}
	if !n.queue.Empty() {
		return fmt.Errorf("%d hooks undelivered after %d passes",
			n.queue.Len(), FlushPassesMax)
	}
	return nil
}
$ tiger check ./...
notifier.go:18:3: TS-L09 [advisory]: escape //tiger:batched — "provider offers
no bulk endpoint; contract caps us at 10 rps" (unverified claim; standing review)
exit status 0 — build is green; the advisory never fails the run and never leaves the report

Read what happened. The unbounded loop got a real fix — a named budget and an error path that turns "hangs forever in production" into "fails loudly with a count." The world-constrained loop kept its shape, but the claim justifying it is now on the record: the build is green, and every future run still prints the escape so the claim can be re-examined when the world changes. Nothing was silenced anywhere in this story.

Message wording The finding texts above are illustrative — exact wording belongs to each analyzer. The contract is the content: rule ID, position, what fired, and the compliant form.

Quick reference

SituationYour move
A rule fired and the code has the banned shape Fix the code — the finding names the compliant form.
A loop is correct but its bound lives in your domain knowledge Make the bound real: an explicit cap constant + an assert on exhaustion. No directive exists for this, on purpose — a trust-me comment can't be checked.
A loop genuinely runs forever (server, event loop) The TS-S03 shape: select on ctx.Done(). Also no directive.
The outside world forces per-iteration IO (no bulk endpoint exists) //tiger:batched <the constraint> on the loop — the one escape hatch. It stays visible as an advisory finding on every run.
You wrote a directive but no reason That's a finding too (TS-L09). Write the real reason — it's the point.
You're sure the finding is a false positive File a bug against the analyzer. Blocking rules are held to a zero-false-positive bar; your report is how it stays there.
You want to silence a finding you'd rather not fix There is no way to do this, on purpose. Fix it or make the case that the rule is wrong.
