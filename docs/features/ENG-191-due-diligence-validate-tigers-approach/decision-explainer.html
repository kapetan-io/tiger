What tiger's static analysis can hold

You are the reviewer ratifying ENG-191. This page walks the five calls you need to make, the evidence each one rests on, and what changes for every registered rule if you say yes. Read the first two sections and you have enough to decide; the rest is the reasoning you can check.

What lands on your desk

One answer to "does rule-based static analysis get tiger its goal," five calls to ratify or veto, a disposition for each of the 40 registered rule codes, and a resolution of the three explainer disagreements. No rule, analyzer, or spec text changes in this PR.

What produced it

Both trial reports and their reruns, a fresh run of today's tiger against the querator pin, two fixture probes against the same binary, the twelve ADRs, the spec's own limits section, and the eleven canceled tickets.

The answer, in one picture

The question underneath the ticket is whether static analysis, as tiger practices it, produces AI-written Go that either conforms or produces a blocking finding the agent must fix. The evidence sorts tiger's rules into four classes, and the answer differs for each.

blue what the machine settles. green what review settles, by design. red where the tool crossed the line and has to come back.

The line The spec's own framing survives contact with the evidence. Machines check the correspondence between code and declaration. Humans and AI agents review whether the declaration is right. Every place tiger went wrong is a place it crossed that line, in one direction or the other.

The worked example: TS-V01

This is the one rule the decision changes, so here is the whole case as the tool shows it. Three loops in one fixture package, run against the same binary as the querator numbers above.

// a cursor drain carrying the escape ADR-0004 admitted for exactly this shape
//tiger:batched store exposes only a per-item cursor
for it.Valid() { keys = append(keys, it.Key()); it.Next() }

// a two-pointer reversal; TS-S02's wave-1.5 grammar accepts this as bounded
//tiger:variant j - i
for i, j := 0, len(b)-1; i < j; i, j = i+1, j-1 { b[i], b[j] = b[j], b[i] }

// integer division toward zero
//tiger:variant n
for n > 0 { n /= 62; count++ }

cursor.go:24:2: TS-V01: //tiger:variant j - i doesn't provably shrink on every pass (no term in the expression provably decreases) — add a cap …
cursor.go:32:2: TS-V01: //tiger:variant n doesn't provably shrink on every pass (n cannot be shown to move consistently) — add a cap …

Today

The //tiger:batched waiver clears TS-S02 and the loop stays blocked under TS-V01. Two correct variant pins are rejected. The only exit the rule offers is an artificial iteration cap, the "magic number or restatement of however big the store is" that ADR-0004 refused for cursor loops.

On querator: 37 findings, 30 of them the loops TS-S02 already handles, 0 bugs. The one real termination bug, a for { select }, is outside V01's scope by design.

After the decision

Variant synthesis is a computed fact, printed under --show-facts and frozen by tiger pin. A pinned variant is verified in both directions exactly as now. An unpinned loop that TS-S02 accepts is not a finding.

Same model as effects and frames: absence of a pin is never a finding. Removes 37 findings from querator, restores the waiver, keeps every guarantee a pin gives.

Why this is not a tuning problem A prover small enough to be exact is too small to verify the loops people write, and growing it is the "exponential in the tail" cost the spec's own honest-limits section names. Two rules currently apply two different termination grammars to the same loop, and the stricter one has no escape.

The three explainer disagreements

These triggered the ticket. Each resolves as part of the larger answer rather than as a patch.

//nolint

Spec: allowed with a reason via nolintlint.
Explainer: banned outright, "tiger flags any //nolint."
Code: tiger check ignores it; under the golangci plugin //nolint:tiger silences a rule with no count.

Resolution. Tiger's own rules accept no suppression under any driver; a bare //nolint or one naming tiger is a blocking TS-L09 finding at the package clause. On auto rules, //nolint:<linter> // reason stays permitted and is counted as TS-L09-escape against the budget. No uncounted silence.

//tiger:restrict

Spec, reference, code: opt-in intent declaration; TS-P01, P02, K03; absence never a finding.
Explainer: removed in commit b452818, with the "How review divides" section built on it.

Resolution. Keep the shipped design. Closed dispatch as a default fails on querator's four backends behind one interface. The TS-P02 precision bound only means anything as a claim. The directive is consumed by two analyzers with corpora. The explainer restores the paragraph. The one half-right point: reflection is already banned by default through TS-S12's auto rule.

Map order

Explainer and code: ban every map range unless the body matches a closed allowlist of order-insensitive shapes.
Spec: "range over a map whose body appends or writes. Heuristic."

Resolution. Not a product disagreement. The ENG-150 blueprint made the inversion on purpose and flagged the spec line for amendment; the amendment never landed. Fix the spec. One wording correction goes the other way: the check is exact over its allowlist, not a heuristic, and the explainer should say so and keep the TS-T11 double-run backstop.

Where an LLM belongs

The ticket asked whether some goals need LLM-judged review.

Resolution. Whether a declaration is true is already assigned to review, and the reviewer may be a human or an AI agent reading the pull request. Tiger owes that reviewer a surface that is small, visible on every run, and impossible to shrink without a diff. It should not judge the claims itself; a model inside the gate makes the verdict nondeterministic and turns the one thing agents cannot fake, a green run, into something they can argue with.

What does not ship

  • No generic //tiger:<rule-id> deviation directive. ADR-0003's admission test holds; nothing in either trial produced a finding a compliant rewrite could not clear, except the cursor loops ADR-0004 already covers.
  • No per-site config exemption for signatures pinned by third-party interfaces. One func literal in one repo; an adapter function is the compliant shape.
  • No blocking-finding baseline for brownfield adoption. A baseline is the mechanism ADR-0011 refused for advisories, and the argument is the same.
