Tiger Rule Set Decision

This document asks you, the reviewer of the pull request, to ratify or veto a short list of specific calls about tiger's rule-based static analysis. It also assigns a stated disposition to every registered custom rule tiger ships. Ratifying it changes what a few rules check, retires one rule as a blocking check, and demotes one rule to advisory, while leaving the rest exactly as they run today.

What you touch versus what the decision computed to get here

The pull request under review is the decision document itself plus the rule-set table it produces. You do not need to rerun the trials, replay the fixture probes, or re-derive the sufficient/insufficient argument to cast a vote. Those are the working parts behind the claims, not the claims themselves.

What you decide on the PR

Five explicit calls, and a disposition for all forty registered rule codes. Your vote is ratify or veto on the document as a whole, or on any one of the five calls it names.

What produced these claims

Two independent trial codebases and their reruns, a fresh run against the same pin used in the first trial, two synthetic fixture probes, and the specification's own "machines check correspondence, humans review declarations" split applied to every rule in the registry.

The three documentation disagreements this decision resolves

Three source documents made three different claims about the same behavior. Two of the three feed directly into the calls above; the third is a wording fix with no behavior change attached.

//nolint

The specification allows //nolint with a reason, enforced by nolintlint under TS-L09. The explainer said tiger bans it outright and flags any //nolint as a finding. Neither matched the shipped code, which does not read //nolint at all under tiger check, and under the golangci-lint plugin lets a //nolint:tiger comment silence a tiger rule with no advisory and no count. The resolution above makes the explainer's sentence true for tiger's own rules and closes the uncounted gap for auto rules.

//tiger:restrict

An earlier explainer commit removed every mention of the directive and asserted that its two axes are not opt-in. The specification, the rule reference, and the shipped code all treat the restriction set as an opt-in declaration where absence is never a finding. This decision keeps the shipped design and asks the explainer to restore the paragraph a reader needs in order to understand TS-P01 in the rule reference.

Map order

The explainer described maporder as a heuristic that bans every map range except a fixed set of safe body shapes. The specification's TS-T02 line calls the same check a heuristic too. The shipped code does what the explainer says, exactly. This is not a product disagreement between the three documents; the specification's wording is stale and the fix is to correct that line rather than the explainer or the code.

The evidence behind these calls

The decision applies one dividing line to every rule in the registry, taken from the specification's own framing that machines check correspondence between code and a stated shape while humans and AI review whether a declaration is true. Every place tiger has gone wrong is a place a rule crossed that line in one direction or the other.

Two fixture probes

Run against the same binary, the probes check a claim the fresh run raised. A cursor loop carrying //tiger:batched, a two-pointer reversal with i, j = i+1, j-1, and a for n > 0 { n /= 62 } loop all fire TS-V01. Pinning //tiger:variant j - i on the reversal and //tiger:variant n on the division is rejected as unverifiable. The only exit the rule offers is an artificial iteration cap, the same shape ADR-0004 already rejected for cursor loops as either a magic number or a restatement of however big the store is.

Follow-ups, in order

  1. TS-V01 to pin-only. Registry and analyzer change; rerun the querator pin and record the count.
  2. ENG-177, all four items. Corpus cases for each recognized shape plus known-miss files for shapes deliberately not recognized; rerun both pins.
  3. Shape exemptions for TS-E02, TS-N07, TS-C09, each with a corpus case naming the excluded shape.
  4. Silencing channels. ENG-178 items 2, 3, 4 and ENG-179 item 1, plus counting //nolint:<linter> as TS-L09-escape.
  5. TS-X01 to advisory, one registry line, and the git-server rerun that decides it.
  6. TS-T02 allowlist growth from the querator sample, by corpus case.
  7. Specification reconciliation, one ticket, covering the TS-T02 enforcement line, TS-V01, TS-L09's //nolint wording, the restriction-set defaults, TS-X01's severity, and the ENG-181 gaps.
  8. Explainer reconciliation, one ticket, restoring the //tiger:restrict paragraph, splitting the //nolint sentence, replacing "heuristic" on map order, and removing the "covers nearly every real loop" claim.
  9. An ADR recording the pin-model rule for provers, that a rule needing a proof the analyzer cannot always construct ships as a computed fact, never as an unpinned finding.
